# Phase 30: Backend Bootstrap and Runtime Assets

## Scope

Make fresh PostgreSQL deployment, unhealthy-startup handling, share-card assets, production dependencies, and badge side effects reproducible.

## Finding-to-test traceability

| Finding | Change | Required evidence |
| --- | --- | --- |
| OB-BE-001 | Advisory-locked bootstrap then ordered migrations | Empty DB, existing DB, rollback/re-upgrade, concurrent deploy, interruption tests. |
| OB-BE-002 | Branch startup on `healthResult.healthy` | Unhealthy DB exits without listener, workers, or scheduler. |
| OB-BE-003 | Copy validated assets into `dist` | Built-artifact landing and card render smoke tests. |
| OB-BE-004 | Replace invalid font with licensed font | Signature/parser check and uncached Satori render. |
| OB-BE-007 | Upgrade audited dependency graph | Node 24 `npm audit --omit=dev` has zero unresolved findings. |
| OB-BE-008 | Return insert outcome before emitting badge effects | Concurrent same-user award test. |

## Acceptance criteria

- `migrate:deploy` holds one advisory lock across an idempotent bootstrap ledger and the legacy chain.
- The production build contains valid runtime assets and cannot serve while database health is false.
- Production dependency audit is clean and duplicate badge effects are impossible for a conflicted insert.

## Evidence boundaries

Disposable services demonstrate code behavior only; Railway deploy, R2, third-party provider, and production data evidence remain Phase 34 requirements.

## Deployment and rollback

Use forward-compatible migrations with a tested downgrade/re-upgrade path. If runtime validation fails, roll back the application image; do not delete user data or bypass the bootstrap ledger.
