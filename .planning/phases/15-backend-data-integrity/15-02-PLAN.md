# Phase 15 Plan 2: Console-to-Winston Logger Migration

Requirements: BETA-19

## Context

The backend has 353 `console.log/error/warn` calls across 62 source files that bypass the existing winston logger utility at `backend/src/utils/logger.ts`. This makes production debugging difficult -- console output is unstructured, has no timestamps, no log levels, and no file rotation. The winston logger is already configured with daily rotation, JSON formatting, and level-based transports but is only used by 16 files.

### Scope

**Migrate (62 files):** All backend source files (`backend/src/`) excluding tests and pure CLI scripts.

**Skip (keep console):**
- `backend/src/__tests__/**` -- test files
- `backend/src/scripts/seed.ts` -- CLI script
- `backend/src/scripts/seed-demo.ts` -- CLI script
- `backend/src/scripts/migrate.ts` -- CLI script
- `backend/src/scripts/migrate-events-model.ts` -- CLI script

**Include:** `backend/src/scripts/retentionJob.ts` -- background process, not a CLI script.

### Logger utility API

```typescript
// File: backend/src/utils/logger.ts
import logger from '../utils/logger';                           // default export: winston logger instance
import { logError, logInfo, logWarn, logDebug } from '../utils/logger'; // named convenience wrappers

// Convenience wrappers accept (message: string, meta?: any)
// They handle non-object meta arguments safely (unlike raw winston)
```

### Migration mapping

| Console Pattern | Logger Replacement |
|---|---|
| `console.log('message')` | `logger.info('message')` |
| `console.log('message', data)` | `logger.info('message', { data })` |
| `console.error('message', error)` | `logger.error('message', { error: error instanceof Error ? error.message : error, stack: error instanceof Error ? error.stack : undefined })` |
| `console.error('message:', error)` | `logger.error('message', { error })` -- OR use `logError('message', error)` convenience wrapper |
| `console.warn('message')` | `logger.warn('message')` |
| `console.log(\`template ${var}\`)` | `logger.info(\`template ${var}\`)` |

**Pitfall:** Winston's `logger.error(msg, meta)` expects an object as second arg. The convenience wrapper `logError(msg, meta)` accepts `any` and is safer for migrating `console.error('msg', error)` calls. Prefer `logError`/`logInfo`/`logWarn` convenience wrappers when the second argument is not already a plain object.

**Action:**

1. **Add import** (skip for ShareController.ts and index.ts which already import):
   ```typescript
   import logger from '../utils/logger';
   ```
   Use the default `logger` import for controllers since most have both info and error calls. For middleware files with only error calls, use `import { logError } from '../utils/logger';` instead.

2. **Replace all console calls:**
   - `console.log(...)` -> `logger.info(...)` (general logging)
   - `console.error(...)` -> `logger.error(...)` (error logging)
   - `console.warn(...)` -> `logger.warn(...)` (warnings)

3. **Handle error objects properly.** When the second argument to console.error is an Error or unknown catch variable:
   - If the catch block catches `error` and does `console.error('Something failed:', error)`:
     Change to: `logger.error('Something failed', { error: error instanceof Error ? error.message : String(error), stack: error instanceof Error ? error.stack : undefined })`
   - OR use the simpler convenience wrapper: `logError('Something failed', error)` -- but then import `{ logError }` instead of default logger.

4. **Contextual log levels** -- some `console.log` calls in controllers are debug-level (request logging, query results). Convert those to `logger.debug(...)` instead of `logger.info(...)`. Examples:
   - Request parameter dumps -> `logger.debug`
   - "Entering function X" -> `logger.debug`
   - "Successfully completed X" -> `logger.info`
   - "User X did Y" -> `logger.info`
