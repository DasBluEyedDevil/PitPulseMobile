# Phase 15 Plan 1: Service Data Integrity Fixes

Requirements: BETA-16, BETA-17, BETA-18

## Context

Three discrete data correctness bugs that could surface during beta testing:

1. **BETA-16** -- Blocked users leak into Wrapped friend overlap stats. `WrappedService.getFriendOverlap()` joins on `user_followers` but never excludes blocked users. The block filter pattern (`BlockService.getBlockFilterSQL()`) is already used in 5 other call sites across 3 services.

2. **BETA-17** -- Semantic mismatch. The DB column `total_reviews` stores a count of reviews, but the API field is named `totalCheckins` and the mobile UI labels it "Check-ins". The data is reviews, not check-ins. Fix: rename the API field to `totalReviews` and update mobile labels to "Reviews". This does NOT affect the User type's `totalCheckins` (which correctly counts actual check-ins) or the `getVenueStats`/`getBandStats` methods (which correctly query from the checkins table).

3. **BETA-18** -- Missing idempotency guard on `ReviewService.respondToReview()`. The UPDATE unconditionally overwrites `owner_response`. Fix: add `AND owner_response IS NULL` to the WHERE clause and throw 409 ConflictError when a response already exists.

### Task 3: Add idempotency guard to ReviewService.respondToReview() [BETA-18]

**Files:**

- `backend/src/services/ReviewService.ts`

**Action:**

1. Add `ConflictError` to the existing import from `'../utils/errors'` (line 6). Currently imports `NotFoundError, ForbiddenError` -- add `ConflictError`:

   ```typescript
   import { NotFoundError, ForbiddenError, ConflictError } from '../utils/errors';
   ```

2. In `respondToReview()` (line ~530), modify the UPDATE SQL to add an atomic guard. Change:

   ```sql
   UPDATE reviews
   SET owner_response = $1, owner_response_at = NOW(), updated_at = CURRENT_TIMESTAMP
   WHERE id = $2
   RETURNING ...
   ```

   To:

   ```sql
   UPDATE reviews
   SET owner_response = $1, owner_response_at = NOW(), updated_at = CURRENT_TIMESTAMP
   WHERE id = $2 AND owner_response IS NULL
   RETURNING ...
   ```

3. After the UPDATE, add the conflict check. Replace the direct return with:

   ```typescript
   if (updateResult.rowCount === 0) {
     throw new ConflictError('A response already exists for this review');
   }

   return this.mapDbReviewToReview(updateResult.rows[0]);
   ```

   This is atomic -- no TOCTOU race condition. If two concurrent requests hit this, the DB ensures only one succeeds.

**Verify:**

- `cd backend && npx tsc --noEmit` compiles without errors
- Grep confirms: `grep -n "owner_response IS NULL" backend/src/services/ReviewService.ts` shows the guard
- Grep confirms: `grep -n "ConflictError" backend/src/services/ReviewService.ts` shows the import and throw

**Done:**

- `respondToReview()` returns 409 Conflict if a response already exists
- Guard is atomic via SQL WHERE clause (not check-then-act)
- Existing behavior for first response unchanged (200 + review data)
