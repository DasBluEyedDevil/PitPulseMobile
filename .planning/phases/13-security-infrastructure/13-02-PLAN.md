<task type="auto">
  <name>Task 2: Add gitleaks configuration for secret detection</name>
  <files>.gitleaks.toml</files>
  <action>
Create `.gitleaks.toml` at project root:

```toml
# Gitleaks configuration for SoundCheck
# Run: gitleaks protect --staged (pre-commit)
# Run: gitleaks detect (full repo scan)
# See: https://github.com/gitleaks/gitleaks

title = "SoundCheck Secret Detection"

[extend]
# Use the default gitleaks ruleset (covers API keys, tokens, passwords, etc.)
# No custom rules needed — the defaults catch the patterns we care about.

[allowlist]
description = "Global allowlist for test fixtures and example files"
paths = [
  '''\.env\.example$''',
  '''backend/\.env\.example$''',
  '''\.gitleaks\.toml$''',
  '''node_modules/''',
  '''backend/dist/''',
  '''mobile/build/''',
  '''\.planning/''',
]

# Allow the bcrypt sentinel reference in migration comments/strings
# (the migration intentionally references '$SOCIAL_AUTH$' to find and replace it)
regexes = [
  '''SOCIAL_AUTH''',
]
```

Also add a gitleaks CI step to the workflow. Append after the backend job in `.github/workflows/ci.yml`:

```yaml
  secret-scan:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
      with:
        fetch-depth: 0

    - name: Run Gitleaks
      uses: gitleaks/gitleaks-action@v2
      env:
        GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

**Note on local pre-commit hook:** The `.git/hooks/` directory is not tracked by git. Rather than creating a non-portable local hook, the CI-based gitleaks check provides the same protection in a reproducible way. If the developer wants local pre-commit detection too, they can run:

```bash
# Windows (after installing gitleaks via winget/scoop/chocolatey):
# gitleaks protect --staged
```

A setup instruction can be added to the README if desired.
