# Plan: Resolve Architectural Diagnostic Findings

## Source

- Request: Create a detailed plan to address every issue in `plans/architectural-diagnostic-report.md`.
- Scope from report: backend API, WebSocket server, BullMQ workers, Redis/cache/rate-limit/Pub/Sub flows, Ticketmaster ingestion, R2 media confirmation, push notifications, mobile auth/startup/router/providers, Dio error parsing, and RevenueCat subscription state.
- Repository guidance reviewed: `AGENTS.md`, `docs/agent/README.md`, `docs/agent/ARCHITECTURE.md`, `docs/agent/CONVENTIONS.md`, `docs/agent/TESTING.md`, `docs/agent/HARNESS.md`, `docs/agent/QUALITY.md`, and `docs/agent/PLANS.md`.
- Read-only code exploration confirmed the report findings and identified test seams and exact implementation locations.

## Goals

1. Restore real-time features by aligning WebSocket authentication, room membership, room validation, reconnect/logout behavior, and multi-instance fan-out.
2. Stabilize push notifications by making initialization idempotent, unregistering tokens on logout, enforcing single-token ownership, and delivering deep-linkable payloads.
3. Normalize backend/mobile API contracts so validation, auth, conflict, rate-limit, and server errors share one parseable shape.
4. Harden long-running and external-provider flows, especially Ticketmaster recursion/rate limiting and R2 photo confirmation.
5. Reduce Redis bottleneck risk by replacing blocking scans and high-fan-out cache deletes with safe patterns.
6. Make subscription UX resilient to RevenueCat webhook lag by separating local purchase UX from server-authoritative entitlement checks.
7. Add regression tests, observability, health details, and rollout safeguards for every corrected contract.

## Non-Goals

- No platform rewrite or replacement of Express, Riverpod, BullMQ, Redis, Dio, GoRouter, Firebase, RevenueCat, or R2.
- No redesign of feature UI beyond the minimum state/navigation changes required for realtime and push behavior.
- No edits to generated Dart files by hand. Regenerate them with `build_runner` if provider annotations or models change.
- No reliance on backend `dist/` as source of truth.

## Recommended Decisions

These decisions keep the plan executable without requiring additional product input.

| Decision | Recommendation | Rationale |
|---|---|---|
| WebSocket auth transport | Keep backend pre-upgrade JWT validation and send the mobile JWT as a URL query parameter using `ApiConfig.wsBaseUrl`. | Backend already supports query tokens, Flutter/WebSocket header support is less portable, and rejecting unauthenticated upgrades is the stronger posture. |
| WebSocket auth acknowledgement | Backend should send an `authenticated` event immediately after a JWT-authenticated upgrade. Mobile should not depend on a post-connect `auth` message for initial auth. | The server already validated the token before accepting the connection; the client still needs an authenticated state transition. |
| Same-event room semantics | Treat `event:<id>` room membership as active attendance/current check-in context, not merely event-detail page viewing. | Joining on page view would cause false "is here too" alerts for users only browsing an event. |
| Check-in room authorization | Add strict UUID room validation immediately. Add DB-backed visibility checks if hidden/private/blocking rules can affect check-in visibility. | The room prefix bug must be fixed now; authorization should not add SQL directly to `websocket.ts`. |
| Device-token unregister on logout | Best effort before clearing auth credentials; failures are logged and do not block logout. | Privacy risk is reduced while preserving reliable logout. |
| Device-token ownership | One FCM token should belong to one current user. Registering the same token for another user should transfer ownership. | Prevents pushes for a previous account on shared devices. |
| Push deep links | Use canonical internal route paths in a `deepLink` field and keep `checkinId`/entity IDs as secondary compatibility fields. | Mobile already has route parsing expectations and GoRouter routes for these paths. |
| Error envelope | Standardize backend failures as `{ success: false, error: { code, message, details? } }`. Mobile parser stays backward-compatible with string errors during rollout. | Enables stable UX and contract tests without breaking older responses mid-transition. |
| Cache invalidation | Implement versioned feed cache keys as the durable fix. Bounded concurrency alone is acceptable only as an interim guard. | Version increments avoid Redis-wide pattern delete storms and old cache keys expire naturally. |
| Premium entitlement | RevenueCat local state can drive purchase UX, but server subscription status must gate backend-authorized features. | Backend webhooks are authoritative for protected endpoints and can lag local entitlement updates. |

## Deployment And Rollback Notes

1. WebSocket fixes are coordinated backend/mobile changes. Backend currently rejects unauthenticated upgrades, so old mobile is already broken for WebSockets; backend authenticated acknowledgement plus mobile query-token upgrade restores behavior without weakening security.
2. Backend can safely accept `checkin:` rooms before mobile starts joining them.
3. Mobile error parsing should be backward-compatible and can ship before backend error-envelope standardization.
4. Push payload fields are additive and can ship before mobile navigation bridge changes.
5. Device-token uniqueness requires a migration with duplicate cleanup. Roll back by dropping the unique token constraint and restoring the previous upsert only if needed.
6. Versioned feed cache keys are safe to roll back because old keys expire by TTL. During rollback, stale versioned keys remain unused until TTL expiration.
7. Ticketmaster limiter/recursion changes may reduce ingestion volume in high-density windows by truncating instead of recursing forever. Monitor truncation logs and retry targeted regions manually if needed.
8. R2 HEAD verification may reject confirmations that previously produced broken URLs. This is intended. If R2 transient failures are noisy, tune retry/backoff rather than disabling existence verification.
9. Subscription changes should not remove local purchase UX. If server sync lags, users should see a syncing/retry state rather than losing access silently.

## Residual Risks To Track

- WebSocket room authorization may require more product/security decisions if check-in visibility rules are broader than public/authenticated visibility.
- Same-event semantics should remain active-attendance based unless product explicitly wants page viewers to receive same-event alerts.
- Firebase and local-notification APIs are static-heavy, so mobile push tests may require adapter seams before reliable unit coverage is possible.
- Error-envelope standardization may require many test expectation updates because older tests may assert string `error` values.
- Versioned cache keys trade immediate delete cost for short-lived old keys until TTL expiration. This is intentional but should be monitored for memory pressure.
- Ticketmaster truncation prevents runaway recursion but may still miss events in extremely dense windows. Truncation metrics must be monitored after rollout.
- R2 HEAD checks add latency to photo confirmation. Use bounded parallel HEAD requests and clear retry semantics for transient errors.
